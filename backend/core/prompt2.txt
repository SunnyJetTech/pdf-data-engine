## 2. Project architecture and existing decisions

DataSage is a multi-tenant data platform with document ingestion, datasets, search, AI/chat, API keys, webhooks, usage/quota management, subscriptions, and payments.

The backend already contains models, repositories, services, schemas, authentication, and some router implementations.

The intended request flow is:

`Router → Service → Repository → Model/Database`

External integrations belong in their appropriate services. Background jobs should use independent database sessions rather than request-scoped sessions.

Use the existing FastAPI, SQLAlchemy, Pydantic, PostgreSQL, and other project dependencies. Do not introduce a new framework without a compelling reason.

## 3. Work already reviewed

The following areas have been reviewed or partially implemented. Verify the actual files before changing anything.

- **Processing jobs:** A `ProcessingJobService` was introduced to wrap the existing repository, and read-only job routes were planned.
- **Documents:** `DocumentService` and `DocumentRepository` handle document operations and processing state. Verify that creation uses the correct `created_by` field and that deletion actually deletes the record.
- **Search:** `SearchService` owns search, context retrieval, search history, and saved-search operations. Saved-search endpoints belong in `search.py`; do not create a redundant router without a reason.
- **Chat:** `ChatService` manages sessions, while `ChatMessageService` manages messages. Tenant ownership must be checked through the associated dataset.
- **AI:** `AIService`, prompt-building, conversation memory, and tool execution have been reviewed. The current codebase's actual provider/tool contracts must be verified before extending them.
- **Exports:** An existing `ExportService` is oriented toward tool execution and writes files locally. Do not invent export models, repositories, or download URLs.
- **Usage and quotas:** Read-only current-tenant usage and quota endpoints have been planned. Administrative mutations should remain protected.
- **Subscriptions:** `SubscriptionService` handles subscription records and plan changes. Public mutation routes must be coordinated with payment processing.
- **Payments:** `PaymentService` exists and handles local payment records and subscription fulfillment. We were about to improve its provider integration and payment router.

Some legacy modules have already been deleted, including Mongo-specific repositories/utilities, a duplicate repository, an export repository, and an upload service. Do not recreate deleted files automatically.

## 4. Current stopping point: payment integrations

This is the immediate area to continue.

We discussed supporting **three payment providers**, allowing a customer to choose the provider most suitable for them. Paystack is the first provider whose integration code has been supplied.

The supplied `PaystackService` has these responsibilities:

- Initialize a transaction through Paystack.
- Verify a transaction using its reference.
- Validate Paystack webhook signatures using HMAC-SHA512.
- Determine whether a provider response represents a successful payment.
- Extract the checkout authorization URL.

The supplied implementation uses `requests` and `core.config.settings`, with settings including `PAYSTACK_SECRET_KEY` and `PAYSTACK_CALLBACK_URL`. The URL in the pasted code was Markdown-formatted and must be corrected to the actual string `https://api.paystack.co`.

Do not assume all configuration settings, models, or provider enums are correct until you inspect the files.

### Third: update `PaymentService`

The central payment service should coordinate the chosen provider and existing database services.

It should:

1. Resolve the current tenant and requested plan using trusted server-side records.
2. Determine the amount and currency from the stored plan, never from a client-supplied amount.
3. Generate a unique payment reference.
4. Create a pending local payment record.
5. Initialize the transaction with the selected provider.
6. Return the reference and checkout URL required by the frontend.
7. Verify the provider transaction and validate its reference, amount, currency, and successful status.
8. Fulfill a successful payment idempotently.
9. Coordinate subscription activation or plan changes through the existing `SubscriptionService`.
10. Handle failed, cancelled, pending, and duplicate verification attempts correctly.

Inspect the actual pricing model and payment schema before implementing this flow.

### Fourth: update the payment router

Implement the endpoints supported by the actual contracts. The intended public API includes:

- `POST /payments/initialize` — authenticated tenant initializes a payment for a valid plan and selected provider.
- `GET /payments/verify/{reference}` — verifies a payment belonging to the current tenant.
- `GET /payments/current/latest` — latest payment for the current tenant.
- `GET /payments/current/history` — payment history for the current tenant.
- `GET /payments/current/total-successful` — total successful payment amount.
- `GET /payments/current/successful-count` — count of successful payments.
- `GET /payments/{payment_id}` — fetch a payment only if it belongs to the current tenant.

Static routes must be registered before dynamic routes where necessary.

Use request schemas for initialization rather than accepting arbitrary amounts as query parameters. Never allow the client to mark its own payment successful.

### Fifth: implement webhook handling

Inspect the existing webhook router and provider infrastructure before deciding whether Paystack's payment webhook should be placed there or in a dedicated router.

For Paystack:

- Read the raw request body.
- Verify the signature before trusting the payload.
- Process successful payment events idempotently.
- Verify payment details before activating subscriptions.
- Handle duplicate and out-of-order events safely.
- Return appropriate acknowledgements.

The webhook must not require a normal browser login, but it must be secured through the provider's signature verification and appropriate event validation.

Update settings and dependency declarations only where necessary. Never expose secret keys in responses or logs.

5. **Transactions and time zones:** Review `datetime.utcnow()`, commit/rollback boundaries, and idempotency after completing the current payment work.
6. **Router registration:** Confirm every intended router is included in the application and avoid duplicate or obsolete routes.
